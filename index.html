System Card — Capability Ledger

A capability ledger generated directly from this project's tool registry and model configuration — not hand-written.

What this is

An agent's actual behavior is shaped by more than the model: its tool definitions, system instructions, and model/generation parameters all matter just as much. None of that surface normally gets versioned, diffed, or reviewed with the rigor applied to code — it just drifts. This page is a generated snapshot of that surface, exactly as it exists in the code right now.

Why it matters

Sculley et al.'s "Hidden Technical Debt in Machine Learning Systems" (NeurIPS 2015) names configuration debt (config isn't versioned or reviewed like code) and entanglement / CACE ("Changing Anything Changes Everything" — no input is truly independent) as debt categories specific to ML systems. The same categories reappear in agentic LLM systems, except now the "configuration" is tool definitions, prompts, and model parameters. A real-world example: a published contact-center agent case study fixed three production issues by editing exactly this surface — adding a tool, injecting a guardrail prompt segment — with no recorded way to know afterward which configuration produced which customer interaction.

Everything that goes into an agent must be tracked

That's why Tools is its own top-level view, not something buried inside each agent's page: a tool can be registered — and therefore part of the system's behavior surface — whether or not any agent currently uses it. If it isn't tracked as a first-class thing on its own, you can't reason about it. Agents is where you see how a given agent resolves that shared registry into the specific tools, instruction, and model it actually runs with.
